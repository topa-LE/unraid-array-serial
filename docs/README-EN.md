# 🗄️ Unraid Serial – Unambiguous Device Assignment

**Stable, readable and reproducible drive identities for the Unraid NAS OS.**

> ### About Unraid
>
> **[Unraid OS](https://unraid.net/)** is a flexible operating system for self-hosted servers and Network-Attached Storage (NAS). Among other things, it enables arrays and pools to be built from different drives and also provides a platform for Docker applications and virtual machines.
>
> **Unraid Serial** extends this platform with stable, readable and reproducible device identities for array drives, pools and boot devices.

Unraid Serial generates stable device identifiers for SATA/ATA, USB-SATA and NVMe drives from verified hardware characteristics.

The identifiers are integrated into the running Unraid system through Udev and protected against unintended identity changes by a server-specific **Identity Baseline**.

The project also includes a separate identity path for the Unraid USB boot device, tools for controlled migration of existing array and pool assignments, and persistent boot diagnostics.

> [!IMPORTANT]
> This project changes or extends device identities that Unraid can use for persistent drive assignments. Existing systems must therefore be unambiguously verified or migrated in a controlled manner before activation.

## 🎯 Project Goal

Linux device names such as:

```text
/dev/sda
/dev/sdb
/dev/sdc
/dev/nvme0n1
```

are not suitable as permanent device identities.

Their assignment can change due to boot order, controllers, USB bridges or changes in hardware detection.

Unraid Serial therefore strictly distinguishes between:

> **1 · Temporary Linux device name**
>
> The current device name assigned by Linux, for example `/dev/sda` or `/dev/nvme0n1`.
>
> **2 · Detected hardware identity**
>
> The identity derived from verified hardware characteristics.
>
> **3 · Generated project ID**
>
> The stable and normalized device identifier generated by the project.
>
> **4 · Device assignment stored by Unraid**
>
> The persistent assignment used by Unraid for arrays and pools.
>
> **5 · Explicitly authorized server-specific Identity Baseline**
>
> The server-specific authorization that determines which detected identity may be used persistently.

A device ID is not persistently authorized merely because it can technically be generated.

---

## 🛡️ Safety Principle

The project follows a **fail-closed principle**.

If a hardware identity is missing, contradictory or ambiguous, processing should stop instead of guessing a persistent device assignment.

Before the Identity Baseline is created for the first time, existing array and pool assignments are checked by the Activation Preflight.

An existing valid baseline is **not automatically replaced** by the installation orchestrator.

> [!WARNING]
> A required migration must never be bypassed by placing a new baseline over existing Unraid assignments that have not yet been migrated.

## 🧬 Supported Persistent Identity Sources

| Source | Meaning | Baseline-capable |
|---|---|---:|
| `ATA` | direct ATA/SATA hardware identity | Yes |
| `USB_SAT` | ATA/SAT identity behind USB-SATA | Yes |
| `NVME` | native NVMe hardware identity | Yes |
| `CACHE` | previously verified fallback | No |
| `FLASH` | separate Unraid boot-device path | Separate handling |

`CACHE` is deliberately not permitted for the persistent Identity Baseline.

The Unraid boot device is likewise not included in the normal drive baseline. It has its own isolated Flash-ID path.

More information:

➡️ [Identity Model](IDENTITY-MODEL-EN.md)

## ⚙️ Udev Rules

| Rule | Purpose |
|---|---|
| `59-array-serial.rules` | authorized whole-disk identities for SATA/ATA, USB-SATA and NVMe |
| `61-array-serial-nvme.rules` | renewed NVMe normalization after system-wide rule 60 |
| `62-array-serial-partitions.rules` | stable identity for partitions |
| `63-array-serial-nvme-links.rules` | additional stable NVMe by-id links |
| `64-array-serial-flash.rules` | isolated identity of the Unraid boot device |

The rules are restored from the persistent project installation into the Unraid runtime system on every boot.

## 🚀 Boot Process

The persistent boot process is integrated through:

```text
/boot/config/go
```

The project components are:

```text
boot-log.sh
boot-capture.sh
install-boot.sh
install-flash-id.sh
```

`install-boot.sh` installs the drive rules and initializes only devices whose detected identity matches the valid server-specific baseline.

`install-flash-id.sh` handles only the physical device on which `/boot` resides.

The boot device therefore remains technically separate from the normal array/pool identity path.

## 📦 Installation

### GitHub Bootstrap

Install or update directly from the official repository.

Run on the Unraid server as `root`:

~~~bash
curl -fsSL https://raw.githubusercontent.com/topa-LE/unraid-array-serial/main/scripts/bootstrap.sh | bash
~~~

The bootstrap downloads the project files to the persistent Unraid
boot device and then starts the installation orchestrator.

Installation does not replace any required controlled migration of
existing array or pool assignments.

### Manual Orchestrator Invocation

As an alternative to the GitHub bootstrap, the project files must first be completely present under:

```text
/boot/config/custom/array-serial/
```

on the target Unraid system.

Then run the following as `root`:

```bash
/bin/bash /boot/config/custom/array-serial/unraid-orchestrator.sh
```

> [!IMPORTANT]
> `unraid-orchestrator.sh` does not download or synchronize the Git repository itself. The orchestrator assumes that the current project files are already completely present in the project directory.

Existing array or pool assignments remain subject to controlled safety and migration checks.

On a completely unconfigured new Unraid server without stored array/pool assignments, the dedicated new-server path can automatically create a server-specific Identity Baseline after successful device verification. This procedure was successfully tested on Unraid 7.3.3.

The complete instructions are available here:

➡️ [Installation and Update](INSTALLATION-EN.md)

## ⚠️ Important Note on Migrations

Installing the project and migrating existing Unraid assignments are two different operations.

If an existing stored Unraid ID does not already match the expected project ID, a new baseline must not simply be placed over it.

In this case, the designated array migration path must be used first:

~~~bash
/bin/bash /boot/config/custom/array-serial/unraid-orchestrator.sh --migrate-array
~~~

Only if the run completes successfully with `BEREIT_FUER_REBOOT` should Unraid be rebooted normally:

~~~bash
reboot
~~~

Phase B is continued automatically through the persistent resume hook after the reboot. Internal migration scripts do not need to be invoked manually.

➡️ [Migrating Existing Device IDs](MIGRATION-EN.md)

Array migration uses a controlled multi-phase transaction path. Development testing confirmed persistent slot assignment after reboot.

Existing parity data is not marked as valid without verification. The safe migration path uses parity synchronization, which must be allowed to complete.

The current installation orchestrator was fully executed on an **Unraid 7.3.2 system** with an existing array, pools, NVMe, USB-SATA and USB boot device and was verified across a normal reboot.

After reboot, the following were confirmed, among other things:

- all four persistent project hooks present
- runtime Udev rules installed again
- server-specific Identity Baseline still valid
- baseline unchanged
- separate Flash by-id link present again
- no open array migration resume file
- array subsequently started normally

This practically confirms the complete installation, boot and reboot path of the current orchestrator on the reference system.
